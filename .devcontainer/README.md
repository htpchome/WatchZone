# Combined Integration DevContainer

This repository includes a self-contained development environment for a
combined Home Assistant integration. It provides Python 3.14 for the backend,
Node.js 20 and Playwright for the TypeScript frontend, FFmpeg, Docker access,
Home Assistant, Frigate/go2rtc, GitHub CLI, common diagnostic tools, and the
OpenAI Codex extension.

## Open the repository in the container

1. Open this repository folder in VS Code.
2. Install the **Dev Containers** extension if needed.
3. Run **Dev Containers: Reopen in Container** from the Command Palette.
4. Wait for the image and services to start.
5. Open the OpenAI/Codex panel from the Activity Bar and sign in.

Codex credentials and settings persist across container rebuilds in a Docker
Compose volume scoped to this repository.

Both the OpenAI/Codex VS Code extension and the Codex CLI are installed. The
startup script verifies `codex --version` and installs the CLI automatically if
it is ever missing from a recreated container.

## Rename the project

The development scripts obtain the project identity from
`.devcontainer/project.env`. Change `PROJECT_DISPLAY_NAME` and
`INTEGRATION_DOMAIN` there when renaming the project. The integration domain
must be a lowercase Home Assistant domain such as `camera_hub` or `new_name`.

Once backend code exists, also rename its
`custom_components/<integration-domain>` directory and update the Home
Assistant manifest/domain references inside the integration. Update frontend
package metadata or product-facing text where applicable. Container and volume
names are generated by Docker Compose and are not hardcoded to the product
name.

## Included services

| Service | Address |
| --- | --- |
| Home Assistant | <http://localhost:8123> |
| Frigate | <http://localhost:5000> |
| go2rtc RTSP | `localhost:8554` |
| go2rtc API | <http://localhost:1984> |
| TypeScript dev server | <http://localhost:5173> |

The Home Assistant Config Helper extension connects to the bundled Home
Assistant instance at `http://localhost:8123`. The devcontainer also resolves
the extension's suggested `http://homeassistant.local:8123` URL for existing
VS Code authentication settings. Container startup waits for Home Assistant's
HTTP endpoint before starting the VS Code extension host.

Home Assistant and Frigate use repository-scoped Compose volumes, so they do
not reuse FrigateViewCard's development state. The host ports are the same, so
the startup handoff stops only the labeled FrigateViewCard development Compose
project before this environment claims those ports. Both repositories also use
`shutdownAction: stopCompose`, and their development services do not have
automatic restart policies.

The stock Home Assistant image does not bundle the Frigate Home Assistant
integration. Install and configure that integration in Home Assistant if this
project needs its entities or proxy APIs.

## Supported project layouts

The setup recognizes either a repository-root layout or a split layout:

```text
backend/
  pyproject.toml or requirements*.txt
  custom_components/<integration-domain>/
frontend/
  package.json
  dist/
```

It also supports `pyproject.toml`, `package.json`, `custom_components/`, and
`dist/` directly at the repository root.

## Project dependencies

The backend receives a repository-level `.venv`. Requirements files and an
editable `pyproject.toml` package are installed automatically when present.
The frontend supports npm, pnpm, or Yarn according to its committed lockfile.

The container mounts `.venv` and `frontend/node_modules` from Linux-backed
Docker volumes. This avoids slow small-file writes through Docker Desktop and
prevents Linux native Node packages from being loaded by Windows tools. The
volumes persist across ordinary rebuilds and are populated by `post-create.sh`.
If dependencies need a completely clean reinstall, remove the corresponding
`<repository>-python-venv` or `<repository>-frontend-node-modules` Docker
volume and rebuild the container.

The initial backend development requirements include the same Home Assistant
version as the local service, pytest, coverage, Ruff, mypy, and pre-commit. The
frontend uses TypeScript, Lit, Vite, Vitest, ESLint, Prettier, and Playwright.
These are committed project dependencies, so both local work and CI use the
same toolchain. Import Lit from its public `lit` package; do not depend on Home
Assistant's private, version-sensitive frontend module paths.

## Home Assistant sync

To copy both the Python integration and compiled frontend into Home Assistant,
run:

```bash
bash .devcontainer/sync-integration.sh
```

The Python package is copied to
`/config/custom_components/<integration-domain>` and frontend assets are copied
to `/config/www/<integration-domain>`. If the project provides
`scripts/list-release-assets.mjs`, the sync script uses that inventory;
otherwise it copies the top-level files in `dist/`.

For continuous synchronization:

```bash
bash .devcontainer/watch-assets.sh
```

Override the frontend defaults with `INTEGRATION_DIST_DIR` or
`INTEGRATION_HA_TARGET_DIR` when the project establishes a different build
layout.

## Reset the environment

Use **Dev Containers: Rebuild Container Without Cache** for a clean image
rebuild. To also remove this repository's Home Assistant, Frigate media, and
Codex state, run Docker Compose `down -v` using the project name shown by
`docker compose ls`.
